# Deployed public-feed performance results

Executed September 10, 2026, approximately 18:19–18:25 Asia/Manila, using
k6 v2.1.0 from the Windows development machine. Target:
`https://schoolconnect-backend-5yrj.onrender.com/api/feed?limit=12`.
The deployed frontend bundle identified this API origin.

## Measured results

These are short, reduced-intensity runs on the existing deployment, with no
credentials. Each iteration makes one public-feed GET. Ramp profiles include
1–3 seconds of think time. Setup traffic is excluded below.

| Profile | Scheduled workload | Requests | p95 | p99 | HTTP/application errors | Result |
| --- | --- | ---: | ---: | ---: | --- | --- |
| Load | Up to 2 users, 42s | 17 | 2,792 ms | 3,124 ms | 0% / 0% | Latency targets failed |
| Stress | 2 → 4 → 8 → 2 users, then ramp down; 69s | 66 | 3,108 ms | 3,685 ms | 0% / 0% | Latency targets failed |
| Spike | 2 → 10 users in 1s, 6s peak hold, then recovery; 32s | 30 | 3,207 ms | 3,213 ms | 0% / 0% | Latency targets failed |
| Scalability baseline | 1 journey/request per second, 30s | 30 | 2,833 ms | 2,906 ms | 0% / 0% | Latency targets failed; zero dropped iterations |

Targets were p95 <800ms, p99 <1,500ms, and error rates <1%. These are provisional
engineering targets, not previously agreed service requirements. All 143 workload
requests across these four runs returned HTTP 200 and a successful application
envelope. Successful responses do not mean the performance targets passed.
All four runs reported failed latency thresholds.

The first smoke attempt timed out after 10 seconds during preflight and executed
no workload. A retry allowing 60 seconds for preflight completed one workload
request in 2,351ms, also failing latency targets. A free-service cold start is a
possible explanation for the first timeout, but was not confirmed.

## What this establishes

The public feed continued returning successful responses under the tested small
loads. Its measured response time already exceeded the provisional target at
low concurrency. Investigate endpoint query timing and server/database metrics
before increasing traffic; these measurements alone cannot identify a database,
network, or server bottleneck. Network travel from this development machine is
included in the request timings.

These runs do not establish maximum capacity, a breaking point, or sustained
recovery. The sample sizes and peak holds are small. No server CPU, memory,
database connection, query, dataset-size, or hosting-instance telemetry was
collected. No resource configuration was changed, so the scalability run is only
a fixed-rate baseline; scaling gains and efficiency remain unmeasured.

Authenticated users, event registrations, uploads, WebSockets, and browser page
rendering were not tested. The suite supports authenticated browsing once a
dedicated account is available. Use representative test data and repeat longer
runs on an isolated environment for a defensible capacity report. Repeat identical
rate sweeps before and after changing instance count or compute size to evaluate
scalability, following the README.
